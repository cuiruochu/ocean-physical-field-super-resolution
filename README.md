# 本仓库的目的

本仓库主要服务于“海洋物理场超分辨率”研究中的数据准备阶段。

需要额外说明的是，本仓库当前只针对下面这个研究区域：

- 最小纬度：`0`
- 最大纬度：`45`
- 最小经度：`105`
- 最大经度：`135`

因此，仓库中涉及下载、切分、对齐和样本构造的数据，默认都是围绕这个区域展开的。

它负责的内容包括：

- 下载相关数据集
- 将原始 `nc` 文件切分为便于后续处理的 `npy` 文件
- 完成 ERA5 与 CMEMS 数据之间必要的时空对齐整理
- 生成可用于后续研究的配对样本

本仓库不负责更进一步的内容，例如：

- 神经网络模型设计与训练
- 下游任务构建与评估
- 数值计算模型的部署与使用
- 完整工程系统的落地实现

因此，更准确地说，这个仓库的定位是：

- 为海洋物理场超分辨率研究提供数据集下载、处理与配对样本准备方案

## NC 转 NPY

脚本 `./scripts/split_nc_to_npy.py`，用于把某个 `.nc` 文件按时间维切分成一批 `.npy` 文件。

- 每个 `.npy` 文件对应一个时间点和一个变量
- 文件名格式是 `2026-01-01T00.npy`
- 数据统一转换为 `float32`
- 原始缺失值会继续保留为 `NaN`
- 默认输出目录是项目下的 `./data`，最终会自动拼接成 `./data/nc文件名/变量名/`
- 每个 `.npy` 文件的 shape 是 `(纬度数, 经度数)`
- 当前变量目录会按 `VMDR`、`VTM10`、`VHM0` 分开保存

例如输入文件：

```text
./downloads/analysisforecast_20260101T000000_20260501T000000_lon105_135_lat0_45.nc
```

默认会输出到：

```text
./data/analysisforecast_20260101T000000_20260501T000000_lon105_135_lat0_45/
```

其中目录结构类似：

```text
./data/analysisforecast_20260101T000000_20260501T000000_lon105_135_lat0_45/
  VMDR/
    2025-12-31T18.npy
    2025-12-31T21.npy
  VTM10/
    2025-12-31T18.npy
    2025-12-31T21.npy
  VHM0/
    2025-12-31T18.npy
    2025-12-31T21.npy
```

`pwsh` 示例：

```powershell
uv run python .\scripts\split_nc_to_npy.py `
  .\downloads\analysisforecast_20260101T000000_20260501T000000_lon105_135_lat0_45.nc
```

指定输出根目录时，仍然会自动拼接 `nc` 文件名：

```powershell
uv run python .\scripts\split_nc_to_npy.py `
  .\downloads\analysisforecast_20260101T000000_20260501T000000_lon105_135_lat0_45.nc `
  --output-dir .\my_npy_data
```

上面这条命令最终会输出到：

```text
./my_npy_data/analysisforecast_20260101T000000_20260501T000000_lon105_135_lat0_45/
```

# ERA5 与 CMEMS 变量对应关系

如果从变量定义上看，ERA5 中这三个变量和 CMEMS 波浪产品中的三个变量是可以对应上的：

- `swh` ↔ `VHM0`
- `mwp` ↔ `VTM10`
- `mwd` ↔ `VMDR`

其中：

- `swh` 和 `VHM0` 都对应总显著波高
- `mwp` 和 `VTM10` 都对应平均波周期
- `mwd` 和 `VMDR` 都对应平均波向

所以从“变量类别和物理意义”上说，这三组是可以对应的。

最后还要注意，即使在定义上可以对应，ERA5 和 CMEMS 产品本身的模型、空间分辨率、时间分辨率、同化方案都不同，因此数值结果肯定不会完全相同。

# ERA5 与 CMEMS 数据的时空对齐

ERA5 和 CMEMS 数据在后续进行对比、融合或建模之前，需要先做好时空对齐。

## 空间对齐

空间对齐的第一步，是在下载数据时就指定一致的经纬度范围。

- 下载 ERA5 数据时，需要指定目标经纬度范围
- 下载 CMEMS 数据时，也需要指定同样的经纬度范围

这样在两套数据切分成 `npy` 之后，二者才会覆盖同一个地理区域。

### 经纬度对齐

即使下载时指定了相同的经纬度范围，ERA5 和 CMEMS 数据在数组中的经纬度排列顺序也不完全相同。

下面这两张图，使用的是同一个时间点下的同类型变量：

- ERA5：`swh`
- CMEMS：`VHM0`

对应图片如下：

![CMEMS VHM0](./images/cmems_vhm0_2026-01-01T00.png)

![ERA5 swh](./images/era5_swh_2026-01-01T00.png)

从原始 `nc` 文件中的坐标可以确认：

- CMEMS 数据的数组 `[0,0]` 对应最小纬度、最小经度
- ERA5 数据的数组 `[0,0]` 对应最大纬度、最小经度

也就是说，二者在经度方向上是一致的，但在纬度方向上的排列顺序相反。

由于当前单个 `npy` 文件的 shape 是：

- `(纬度数, 经度数)`

因此，如果要让 ERA5 和 CMEMS 数据在同一地理朝向下进行比较，就需要对 ERA5 的数组做一次“上下翻转”。

这里的“上下翻转”指的是：

- 沿着数组的第一个维度翻转
- 也就是沿着纬度维度翻转
- 如果按二维数组记法理解，就是对 `H` 这一维翻转，而不是对 `W` 这一维翻转

这样处理之后，ERA5 数组左上角对应的经纬度方向，才能和 CMEMS 数据保持一致。

### 数组 shape 对齐

在完成上面的经纬度方向对齐之后，还需要继续关注三类数据的数组 shape。

当前单个 `npy` 文件的 shape 分别是：

- ERA5：`(91, 61)`
- CMEMS 再分析数据：`(225, 151)`
- CMEMS 预报数据：`(541, 361)`

它们的含义都是：

- `(纬度数, 经度数)`

从分辨率上看：

- ERA5 约为 `0.5°`
- CMEMS 预报数据约为 `1/12°`
- CMEMS 再分析数据约为 `0.2°`

因此，在经纬度方向对齐处理好 ERA5 的翻转之后，ERA5 和 CMEMS 在空间采样密度上还存在整数倍或接近整数倍的关系。

对于 CMEMS 预报数据：

- ERA5 对应 shape 是 `(91, 61)`
- CMEMS 预报数据对应 shape 是 `(541, 361)`
- 如果把最大纬度和最大经度对应的一行一列裁掉，那么：
- ERA5 会变成 `(90, 60)`
- CMEMS 预报数据会变成 `(540, 360)`
- 此时二者正好是严格的 `6` 倍关系

对于 CMEMS 再分析数据：

- ERA5 对应 shape 是 `(91, 61)`
- CMEMS 再分析数据对应 shape 是 `(225, 151)`
- CMEMS 再分析数据当前下载结果中的纬度范围是 `0.2°` 到 `45.0°`
- 这意味着它没有像预期那样从 `0.0°` 开始
- 目前可以确认，本项目下载数据集的脚本本身并没有问题；但为什么 CMEMS 再分析数据下载结果是从 `0.2°` 开始，这个原因暂时还不明确

在工程处理上，ERA5 和 CMEMS 再分析数据进行对齐时，仍然可以采用下面这种方式：

- 在纬度方向上，删除 ERA5 中 `0.0°` 对应的那一行
- 删除最大经度对应的一列

这样处理之后：

- ERA5 纬度会从 `91` 变成 `90`
- CMEMS 再分析数据纬度保持 `225`
- 此时纬度方向正好是严格的 `2.5` 倍关系

同时：

- ERA5 经度会从 `61` 变成 `60`
- CMEMS 再分析数据经度会从 `151` 变成 `150`
- 此时经度方向也正好是严格的 `2.5` 倍关系

因此，在完成经纬度方向对齐之后，这样的裁剪方式在 ERA5 和 CMEMS 再分析数据之间是可接受的。

### 备注

- 如果同一份 ERA5 数据分别去对齐 CMEMS 再分析产品和 CMEMS 预报产品，并且都采用“删除最大经纬度对应的行和列”的方式，那么工程上会出现一个问题：
- 同一份 ERA5 数据需要为了对齐这两个 CMEMS 产品而做出不同的裁剪处理
- 这会导致需要额外保存两份不同版本的 ERA5 产品

因此，也可以考虑另一种工程处理方案：

- 统一采用“删除最小经纬度对应的行和列”的方式来处理 ERA5

这样做在工程上仍然是可以接受的，并且只需要处理和保留一份 ERA5 产品，后续管理会更简单。

本项目中也提供了一个针对样本 `npy` 文件的处理脚本：

- `./scripts/align_example_npy_shapes.py`

这个脚本会对三个输入样本分别执行约定好的处理，并把结果输出到 `./tmp`，用于得到 shape 已经完成对齐的三个 `npy` 文件。

## 时间对齐

时间对齐的第一步，是在下载数据时指定一致的时间范围。

- 下载 ERA5 数据时，需要指定目标时间范围
- 下载 CMEMS 数据时，也需要指定同样的时间范围

但仅仅指定相同的起止时间还不够，因为两套数据的时间分辨率不同：

- CMEMS 数据当前使用的是 3 小时分辨率
- ERA5 数据当前使用的是 1 小时分辨率

因此，在下载并切分完成之后，还需要在时间维上再取一次交集。

也就是说，后续真正用于比较的时间点，应当是：

- 同时存在于 ERA5 `npy` 文件集合中的时间点
- 同时存在于 CMEMS `npy` 文件集合中的时间点

只有在完成这一步之后，二者在时间上才算真正对齐。

# 神经网络注意事项

这一部分主要是给后续继续沿用这个数据处理方案的人使用。

- `LR` 可以理解为 ERA5
- `HR` 可以理解为 CMEMS 的两个产品

## 归一化

对于物理场数据，我更倾向于使用 `z-score` 标准化，而不是 `min-max` 归一化。

虽然在很多实验里，`min-max` 归一化的数值效果可能会更好，但它并不适合当前这种物理场场景。原因在于：

- 训练集是模型真正用来学习参数的数据
- 验证集是训练过程中用来调参与挑选模型的数据
- 测试集是最终用来评估模型泛化能力的数据

严格来说，测试集在建模阶段不应该被提前“看见”，尤其，不应该提前知道测试集的统计量。

而 `min-max` 归一化天然依赖全局最大值和最小值，这就会带来几个问题：

- 使用训练集统计出来的全局 `min/max`，那么未来测试集很可能会出现超出这个范围的数据
- 一旦测试集出现超出训练集 `min/max` 的值，归一化结果就会落到 `[0, 1]` 区间之外
- 如果使用“每对样本各自的最大最小值”做归一化，可以保证每对样本都在 `[0, 1]` 区间内，但是不同样本之间的物理幅值关系会被打散

因此，从工程稳健性和物理一致性的角度，我更推荐使用 `z-score` 标准化。

## 上采样算子

主流的 SISR 方法里，经常使用 `pixel shuffle` 作为上采样算子。但在当前这个物理场超分的任务里，它存在两个明显问题。

第一个问题是大倍率上采样不合适。

- `pixel shuffle` 更适合较小整数倍放大
- 对于 `6` 倍这种较大的倍率，直接一次放大会导致可训练参数较多，训练压力更大
- 如果要继续使用这类思路，更合理的方式通常是分两步放大，例如先放大 `2` 倍，再放大 `3` 倍

第二个问题是它不能自然处理非整数倍放大。

- `pixel shuffle` 本质上要求整数倍重排
- 但 ERA5 对齐 CMEMS 再分析产品时，对应的是 `2.5` 倍关系
- 因此 `pixel shuffle` 不能直接作用于这种 `2.5` 倍场景

目前对于 `2.5` 倍这种非整数倍上采样，还没有找到一个特别满意的统一解决方案。

# 我的留言

## 关于这个问题本身的理解

我对这个课题的理解是：物理场超分辨率，本质上可以看作是在尝试替代一部分高分辨率数值求解的过程。

以波浪场中的某个物理量为例，例如 `mwp`。如果希望获得真实的高分辨率物理场数据，传统路径需要以观测数据（例如卫星观测）作为输入，初始化相应的动力学方程组，然后在离散化网格上进行数值求解。不同空间分辨率下，求解同一套方程组所需要的计算资源是完全不同的。求解一个低分辨率物理场，与求解一个高分辨率物理场，在算力开销上往往存在非常大的差异。

从这个角度看，神经网络在这里的意义，并不是替代整个物理过程本身，而是希望替代“直接求解高分辨率物理场”这一部分高成本步骤。也就是说，理想目标是：

- 先通过传统数值求解方法得到低分辨率物理场
- 再由神经网络把低分辨率物理场推理成超分辨率物理场
- 用这个超分辨率结果去近似替代原本代价很高的高分辨率数值求解结果

如果这个方向成立，那么它真正节省的不是简单的图像处理成本，而是高分辨率数值模拟的计算成本。

## 我个人的遗憾

作为研究人员，我对这个方向始终有一个很明显的遗憾：我不会真正意义上的数值求解。

更具体一点说，我甚至无法完整列出这里背后对应的动力学方程组，也没有真正从零部署并成功使用过这些数值求解工具。开源的物理海浪数值求解方法本来就不算多，我目前知道的一些名字包括 `SWAN`，以及`妈祖`这一类相关系统，可能还存在别的方法，但我并不掌握它们的全貌。

更重要的是，我始终没有真正把这些开源方法彻底搞懂，也没有获得“亲手把它们部署起来，并成功跑出结果”的实际经验。对我来说，这是做这个课题过程中一直存在的遗憾。

某种意义上说，我现在做的工作更偏向于“利用已有数据研究从低分辨率场到高分辨率场的映射关系”，而不是完整掌握“这些高分辨率物理场究竟是如何被数值求解出来的”。这一点我认为应该坦诚地留下来，给后续继续做这个方向的人一个真实的背景说明。

## 关于我做过的“合成数据集”方案

在我的硕士毕业论文中，我曾经采用过一种“合成数据集”的方案：

- 对 ERA5 数据做 `Bicubic` 下采样，得到 `LR`
- 把原始 ERA5 作为 `HR`
- 用这样的 `LR-HR` 配对数据训练网络

我需要非常诚恳地指出，这种方案不是一个好的方案。

原因很简单：它无法带来实际的工程落地价值。因为我永远得不到比 ERA5 本身分辨率更高的数据或产品，所以这种做法本质上只是在从 ERA5 的降质版本中“恢复”出 ERA5。它能够说明的，只有一件事：

- 所提出的网络，在这个人工构造出来的 benchmark 上，比别的网络表现更好

除此之外，它几乎什么都无法证明。

## 关于“下游任务”评估的困难

我也没有能够在依赖 `HR` 数据的下游任务上，对 `SR` 数据进行充分评估。

这背后有两个原因。

第一个原因是，下游任务本身往往更偏向“海洋科学领域”，而不是“计算机视觉领域”。作为“软件工程”专业的学生，我很难快速进入这些问题的核心。不仅如此，我甚至没有顺利找到一个真正适合比较 `HR` 和 `SR` 差异性的下游任务。这个“下游任务”本身就不容易调研到，更不用说在调研到之后，还要继续弄懂它、复现它、计算它的结果，并进一步量化评估 `SR` 数据对下游任务误差的影响。

但我仍然要强调，这是我的课题，我本来有义务去研究物理场超分辨率的下游任务。只是因为自己“学识尚浅”，再加上“实习占用时间太多”，最后没有完成这个义务。这是我必须坦诚承认的事情。

第二个原因是，如果只是使用“原始 ERA5”和“恢复出来的 ERA5”去做下游任务，那么这件事本身也不具备太多现实意义。因为原始 ERA5 本来就是人人都可以获取的数据，在已经有原始 ERA5 的前提下，再去构造一个“恢复出来的 ERA5”，然后比较它们在下游任务中的表现，本质上也只是提出了一个新的 benchmark，并没有真正解决“工程落地价值”的问题。

相反，如果能够把“数值计算得到的 HR 结果”和“神经网络计算得到的 SR 结果”放到某个真正依赖 `HR` 数据的下游任务上比较，并证明：

- `SR` 结果在该下游任务中并不明显差于 `HR` 结果

那么在这个下游任务对应的应用场景中，用神经网络去近似替代高代价的数值计算，就是一件真正有现实意义的事情。

## 关于使用 ERA5 对齐 CMEMS 训练的看法

同样的逻辑也适用于当前这种：

- 把 ERA5 当作 `LR`
- 把 CMEMS 的预报数据或再分析数据当作 `HR`

的训练方案。

这种方案比我当初的“ERA5 自己降质再恢复”的合成数据集要更好一些，但它仍然没有彻底解决“工程落地价值”的问题。因为即使这样训练出一个网络，它也仍然不能产生比 `CMEMS` 产品本身更高分辨率的数据。它本质上还是在学习：

- 如何从 ERA5 近似恢复出一个 CMEMS 风格的结果

所以它同样主要只能证明：

- 所提出的网络，在这个新的 benchmark 上，比别的网络更优

除此之外，依然很难直接证明更多东西。

并且，若要把这种 `ERA5 -> CMEMS` 的结果放到下游任务中，困难依然存在。因为你能够比较的，通常也只是：

- `CMEMS` 本身
- 以及“由 ERA5 近似恢复出来的 CMEMS”

这依然不具备特别强的现实价值。

不过，相比我之前的“合成数据集”，这种方式仍然有一个很重要的优点：

- `CMEMS` 预报数据和再分析数据通常是 3 小时分辨率
- ERA5 是 1 小时分辨率

因此，在时空对齐后的样本上完成训练之后，可以在那些“ERA5 有而 CMEMS 没有”的时间点上，超分出一个相对合理的结果。这一点至少说明，这种方案在时间补全层面具备一定潜在价值。

## 我对这个方向最核心的看法

归根结底，我对物理场超分辨率这个方向的矛盾点理解是：

- 神经网络计算出来的 `SR` 结果，永远无法战胜“可以轻易获取的数据”

如果某个 `HR` 数据本身已经是稳定、低成本、可直接获取的，那么再去用神经网络近似它，实际意义通常不大。

但是，“数值计算得到的 HR 结果”恰恰不属于“可以轻易获取的数据”。它往往需要大量的计算资源、时间成本和工程投入。也正因为如此，如果神经网络能够计算出一个“极难获取的 HR 结果”的近似 `SR` 结果，那么这件事才真正体现出神经网络在这个领域里的意义。

## 我对神经网络创新性的看法

神经网络创新本身是一个重要且具备科研价值的工作。我个人也十分认可“面向物理场超分辨率问题进行神经网络创新”这个研究方向。

优秀的神经网络工作，往往并不只是“换一个模块”这么简单。它通常同时涉及几个层面的难点：

- 面向目标平台的算子实现
- 真正有效且高效的算子设计
- 网络结构、训练稳定性与工程可部署性之间的平衡

这些问题本身就非常困难，也确实值得大量研究人员持续投入。

如果把视角放宽到更大的深度学习领域，这一点其实非常明显。即使在当前已经极为成熟、竞争也极为激烈的 `LLM` 领域，围绕神经网络结构本身，依然几乎每年都会出现非常优秀的工作。例如：

- `DeepSeek` 提出的 `MoE shared experts`
- `DeepSeek` 提出的 `MoE bias`
- 阿里 `Tongyi` 提出的 `Gated Attention`
- `DeepSeek V4` 中提出的 `CSA`
- `DeepSeek V4` 中提出的 `HCA`
- `DeepSeek V4` 中提出的 `mHC`

这些工作都说明，神经网络创新并不是一个“已经没有价值”的方向。恰恰相反，它始终是深度学习研究中非常核心的一部分。

只是回到“物理场超分辨率”这个具体问题上，我目前的看法是：在没有先完善好工程落地价值、没有先明确好真正有意义的下游任务之前，过早地去做 `SR` 神经网络创新，是一种比较盲目的做法。

更具体地说，如果连下面这些问题都还没有回答清楚：

- 这个任务最终服务于什么实际场景
- `SR` 结果究竟要替代什么高成本过程
- `SR` 结果在什么下游任务中才算真正有价值
- 一个新的网络结构即使在 benchmark 上更优，是否就能转化为实际价值

那么此时继续强调“网络创新”，很容易变成：

- 在尚未明确目标的问题上，继续优化一个尚未被证明真正重要的 benchmark

这并不意味着神经网络创新不重要，而是意味着在这个具体方向里，问题定义、落地价值和下游任务的确定，应当优先于网络结构本身的创新。
